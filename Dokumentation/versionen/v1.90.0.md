# Version 1.90.0 – Die fremde Lesung auf dem eigenen Bild

Beim Einlesen einer Projektdatei kann eine Kennung schon vergeben sein. Dann
wird die fremde umbenannt, und die Strecken des Pakets werden auf die neue
Kennung umgeschrieben – dafür gibt es `streckenMitNeuenKennungen()`.

Die Frage, die ich nie gestellt hatte: **was hängt sonst noch an Kennungen?**
Nachgefahren mit zwei Beständen, die dieselbe Kennung führen:

```
umbenannt:        AUF-2026-001 -> AUF-2026-002
Eingang danach:   AUF-2026-002 „Fremde Maske" | AUF-2026-001 „Meine Maske"
Strecke zeigt auf: AUF-2026-002 – umgeschrieben
Lesung auf AUF-2026-001 -> trifft „Meine Maske"
ohne Lesung:      AUF-2026-002 „Fremde Maske"
```

Die Lesungen des Registers OCR liegen unter der Kennung der Aufnahme. Sie
wurden unverändert dazugemischt. Das Ergebnis ist nicht „verloren", sondern
schlechter: **der fremde Text landet auf meinem Bild**, und das Bild, zu dem
er gehört, steht ohne da.

Das bleibt nicht im Register OCR. Gelesener Text geht von dort

* in die **Suche über die Lesungen**,
* in den **Agenten** der Prüfung,
* und auf Knopfdruck **in die Notiz** – und von dort ins Handbuch.

Ein falsch zugeordneter Text ist also kein Anzeigefehler, sondern eine
falsche Angabe, die sich fortschreibt.

## Behoben

`ocrMitNeuenKennungen()` schreibt die Lesungen um, wie es die Strecken seit
jeher tun. Danach:

```
Lesung auf AUF-2026-002 -> trifft „Fremde Maske"
ohne Lesung: AUF-2026-001 „Meine Maske"
```

Richtig: für mein eigenes Bild hat nie jemand eine Lesung gemacht.

## Damit es nicht wieder passiert

Die Lesungen waren nicht vergessen worden – es hatte nur nie jemand gesagt,
dass sie auf Aufnahmen zeigen. `PAKET_INHALT` sagt es jetzt:

```js
{ schluessel: STRECKEN_SCHLUESSEL, reist: true, feld: 'strecken', kennungen: true },
{ schluessel: OCR_SCHLUESSEL,      reist: true, feld: 'ocr',      kennungen: true },
```

Der Build hält die Liste gegen `ablage.js`: zu jedem Feld mit
`kennungen: true` muss dort `<feld>MitNeuenKennungen(` aufgerufen werden.
Gegengeprüft, indem ich den Aufruf wieder entfernte – die Prüfung schlägt
an.

Die übrigen sieben mitreisenden Speicher wurden durchgesehen: `projekte`
hängen an Projektnamen, `texte` an Stellen, `regeln` an eigenen Kennungen,
`design`, `wortliste`, `vorgehen` und `verzeichnis` an nichts. Keiner zeigt
auf Aufnahmen.

## Zwei geschärfte Prüfungen statt zweier neuer

Die Zahl bleibt bei 568. Der Fall gehört dorthin, wo das Zusammenführen
schon geprüft wird – *„beim Ergänzen behält keiner sein Bild auf Kosten des
anderen"* –, und die Liste gehört dorthin, wo die Projektdatei schon gegen
`PAKET_INHALT` gehalten wird. Eine neue Prüfung daneben hätte dieselbe Sache
an einer zweiten Stelle beschrieben.

Die Kernprüfung prüft jetzt auch die Umkehrung: **jede Lesung muss nach dem
Zusammenführen wirklich eine Aufnahme treffen.** Das ist die Bedingung, die
der Fehler verletzte, und sie gilt unabhängig davon, wie umbenannt wird.

## Grenzen

* Umbenannt wird nur beim **Ergänzen**. Beim Ersetzen gibt es keine
  Kollision, und `umbenannt` bleibt leer – dann gibt `ocrMitNeuenKennungen`
  dasselbe Objekt zurück, das es bekommen hat.
* Eine Lesung, die schon vor dem Einlesen auf eine Kennung ohne Aufnahme
  zeigte, bleibt liegen. Das Einlesen räumt nicht auf, was vorher
  verwaist war.
