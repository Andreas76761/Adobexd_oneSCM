# Version 1.74.0 – Die Datei war noch nie in Word

Acht Fassungen lang hieß die Frage: *was die Seite schreibt, wieder
hineingeben.* Jedes Mal war die Datei dabei zwischen Schreiben und Lesen
**unberührt** geblieben. Genau das tut sie im Leben nie.

Der Rückweg aus Word (F-65) gibt es, weil die Datei ins Haus geht, **dort
geöffnet und gespeichert wird** und zurückkommt. Also diesmal: die Datei
einmal durch ein echtes Office schicken, bevor sie zurückgeht.

```bash
soffice --headless --convert-to docx handbuch.docx
```

## Elf von elf, wieder

```
Meldung: 11 Stelle(n) gelesen · 11 geändert · 0 unverändert

[geaendert] 7.5.1 Dokumentierte Signaturwege
   alt: (leer)
   neu: Schritt 1 · Vertragsnummer fokussiert
```

Derselbe Befund wie in 1.66.0, durch eine andere Tür: **die
Bildunterschriften wurden als Text der Stelle gelesen.**

## Eine Vorlage hat zwei Namen

Der Grund steht in der Datei selbst:

| | geschrieben von der Seite | nach LibreOffice |
| --- | --- | --- |
| `w:styleId` | `Bildunterschrift` | **`Caption`** |
| `w:name` | `caption` | `Caption` |

Die **Kennung** schreibt jedes Programm anders. Der **Name** ist
festgelegt. Der Leser sah bisher nur die Kennung an, und die war nach
einem Durchlauf eine andere.

Dasselbe gilt für die Überschriften, und dort wiegt es schwerer: erkannt
wurde `Heading1` – nur das. Ein deutsches Word schreibt die Kennung
`berschrift1` (ohne führendes Ü, das ist kein Tippfehler). Eine solche
Datei hätte **gar keine Stelle** ergeben, und niemand hätte es je
bemerkt, weil hier nie ein deutsches Word im Spiel war.

Gelesen wird jetzt `word/styles.xml`: dort steht zu jeder Kennung ihr
Name, und daraus wird die **Rolle** – Überschrift, Bildunterschrift,
Quellhinweis. Fehlt die Datei, wird an der Kennung geraten, und zwar an
den Schreibweisen, die vorkommen (`Heading1`, `berschrift1`, `Caption`,
`Beschriftung`, `Legende`).

Dieselbe Karte bekommt der Import (F-39): auch er teilt ein Dokument an
den Überschriften, und auch er hätte ein deutsches Word nicht geteilt.

## Was dabei in Ordnung war

| | |
| --- | --- |
| `Quellhinweis` | LibreOffice behielt Kennung **und** Namen – die eigene Vorlage aus 1.66.0 überlebt |
| alle 11 `r:embed` | im Text geblieben, kein Bild verloren |
| Import mit derselben Datei | 11 Bilder, **11 verschiedene Stellen** |
| die PowerPoint-Datei | 3 Folien, 3 Bilder, unverändert lesbar |

## Ein Fehler, den ich selbst eingebaut habe

Die erste Fassung las `styles.xml` richtig und fand trotzdem **null**
Stellen:

```js
const ebene = rolle.startsWith('ueberschrift') ? Number(rolle.slice(13)) : 0;
```

`'ueberschrift'` hat zwölf Zeichen, nicht dreizehn – `slice(13)` ergab
einen leeren Text und damit Ebene 0. Aufgefallen beim Nachmessen, nicht
beim Lesen; eine Zahl im Code sieht man nicht an, ob sie stimmt.

## Grenzen – und eine, die bleibt

* Geprüft mit **LibreOffice**, nicht mit Word. Word benennt beim Speichern
  anders um als LibreOffice; welche Kennungen es wählt, steht hier nicht.
  Der Weg über `styles.xml` ist gerade deshalb der richtige: er fragt
  nicht nach der Kennung.
* **Ohne `styles.xml` bleibt es beim Raten.** Eine frei vergebene Kennung –
  im Prüffall `Quelle42` für den Quellhinweis – kann nicht erkannt werden,
  und ihr Absatz landet im Text der Stelle. Das steht so in der Prüfung
  und ist kein Versehen: es ist die Grenze des Ratens und der Grund, warum
  `styles.xml` überhaupt gelesen wird.
* Eine Datei, in der jemand die Überschriften **nicht** als Überschriften
  formatiert, sondern nur fett setzt, bleibt unlesbar. Ohne Vorlage keine
  Rolle – dieselbe Grenze wie seit 1.47.0.
