# Version 1.71.0 – Der offene Punkt aus 1.70.0

1.70.0 fuhr jeden Ausgang von `sample` durch Suchchat und Prüfung und fand
dort einen Fehler. Zwei Register blieben liegen, und das stand ausdrücklich
so in der Versionsnotiz:

> **OCR und Video** ließen sich so nicht fahren: beide brauchen ein Bild
> bzw. einen Film im Browser. Ihre Fehlerwege sind gelesen, nicht gefahren.

Jetzt gefahren. Der Prüfstand legt dafür selbst ein Bild an (Beispielquelle,
auslösen) und öffnet den Messfilm.

## Drei Befunde

### 1. Der Grund wurde eine Zeile später überschrieben

```
OCR  abgelehnt (not_granted)  0 von 1 Bildern gelesen, 1 nicht.
OCR  zu viele (rate_limited)  0 von 1 Bildern gelesen, 1 nicht.
```

Dieselbe Zeile für zwei ganz verschiedene Lagen – einmal *es ist verboten*,
einmal *gleich noch einmal versuchen*. Dabei stand die richtige Antwort im
Code:

```js
if (code === 'rate_limited') {
  meldeOcr('Zu viele Anfragen in kurzer Zeit – später noch einmal …');
  break;
}
…
meldeOcr(`${fertig} von ${bilder.length} Bildern gelesen, ${gescheitert} nicht.`);
```

Der Fangzweig schreibt die genaue Meldung, die **Schlusszeile überschreibt
sie** – sie läuft immer. Die sorgfältige Arbeit wurde eine Zeile später
weggeworfen. Prüfung und Video hatten den Fehler nicht, weil sie keine
Schlusszeile haben. Jetzt steht der Grund voran:

```
Das Lesen wurde nicht erlaubt. Die Felder bleiben zum Eintragen von Hand. 0 von 1 Bildern gelesen.
```

### 2. Eine leere Antwort löschte den vorhandenen Text

```
OCR  leere Antwort  1 von 1 Bildern gelesen.
```

Gelesen wurde nichts. `teile` enthielt einen leeren Text, `teile.length`
war 1, also galt das Bild als gelesen – und dann:

```js
function setzeOcrText(kennung, text, …) {
  const sauber = String(text || '');
  if (!sauber.trim()) delete ocrTexte[kennung];   // ← löscht
```

Eine leere Antwort **löschte** also die Lesung, die vielleicht schon
dastand, und die Seite meldete Erfolg. Das ist die schlimmste Form: ein
Verlust, als Gelingen gemeldet.

Jetzt zählt nur ein nichtleerer Text als gelesen, und die Meldung lautet:
*„0 von 2 Bildern gelesen. Bei 2 hat Claude nichts gelesen – der vorhandene
Text bleibt stehen."*

### 3. Die Fortschrittszeile blieb stehen

```
Video  leere Antwort  Bild bei 00:00,0 wird gedeutet … (1 von 1)
```

Der Lauf war vorbei – der Knopf wieder offen –, aber die Zeile sagte das
Gegenteil. Der Grund:

```js
if (fertig) { meldeVideo(`${fertig} Bilder gedeutet …`); }
```

Kam nichts zurück und scheiterte auch nichts, lief kein Zweig, und die
letzte Meldung blieb die des Fortschritts. Jetzt sagt jeder Ausgang etwas.

## Was die drei gemeinsam haben

Keiner ist ein Absturz. Alle drei sind **Meldungen, die nicht stimmen** –
und zwei davon melden Erfolg, wo keiner war. Dieselbe Regel wie in 1.67.0
und 1.70.0: eine Fehlmeldung ist schlimmer als keine Antwort.

Auffällig ist auch, wo sie saßen: nicht in der Fehlerbehandlung, sondern
**dahinter**. Die Fangzweige waren sorgfältig geschrieben. Was fehlte, war
der Blick auf die Zeile, die danach läuft.

## Was dabei in Ordnung war

| | |
| --- | --- |
| kein Lauf hängt | der Knopf ist in jedem Ausgang wieder offen |
| keine Seite wirft einen Fehler | in keinem der vier Register, in keinem Ausgang |
| „Fähigkeit fehlt" | alle vier sagen genau, was stattdessen geht |

## Grenzen

* Nachgebaut sind vier Ausgänge. `cancelled` hat in OCR und Video einen
  eigenen Zweig (`break` ohne Zählung) und wird über den Abbrechen-Knopf
  geprüft, nicht hier.
* Eine Antwort, die *falsch* ist statt leer, bleibt eine Deutung – sie
  steht im Feld und lässt sich ändern. Das ist Absicht und keine Lücke.
* Gefahren wurde mit **einem** Bild bzw. **einem** Filmbild. Ein Lauf, der
  mitten in zwanzig Bildern abbricht, ist damit nicht gemessen; die Zählung
  (`fertig`, `gescheitert`, `leer`) ist dafür gebaut, aber nicht gefahren.
