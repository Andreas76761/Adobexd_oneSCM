# Version 1.73.0 – Der Zettel zeigte auf nichts

Zwei Wege nach draußen waren noch nie **angesehen** worden: die BPMN-Datei
und der Ordner, den das Register Verzeichnis schreibt. Beide werden von
Prüfungen abgedeckt – und beide Prüfungen zählen, statt hinzusehen.

## Der Ordner

Die Browserprüfung hält von jeder geschriebenen Datei Pfad, Größe und Typ
fest. Den **Inhalt** hat nie jemand gelesen. Also einmal wirklich
geschrieben, in einen echten Zielordner:

```
   97 kB  ohne-sparte/ohne-sprache/7-5-1/ohne-rolle/2026-10-27-auf-2026-001-…-01-00m00s2.png
    1 kB  ohne-sparte/ohne-sprache/7-5-1/ohne-rolle/2026-10-27-auf-2026-001-…-01-00m00s2.json
   …
   10 kB  index.json
    2 kB  index.csv
    1 kB  strecken.json
    9 kB  prozesse/servicevertrag-anlegen.bpmn
```

26 Dateien, Baum und Namen richtig. Und im ersten Beipackzettel:

```json
{ "bild": "AUF-2026-001.png", … }
```

Die Datei daneben heißt
`2026-10-27-auf-2026-001-servicevertrag-anlegen-01-00m00s2.png`.

**Der Zettel nannte eine Datei, die es in seinem Ordner nicht gibt.**

```js
function zettelFuer(aufnahme) {
  return baueBeipackzettel({
    bildname: aufnahme.id + '.png',   // ← fest, am Muster vorbei
```

Zettel und Bild finden sich trotzdem – sie teilen den Dateinamen, nur mit
anderer Endung. Wer aber den Zettel liest, um das Bild zu finden, greift
ins Leere. Genau dafür ist das Feld da (F-28: „Daran wird die Datei
wiedererkannt"). Der Name kommt jetzt aus dem Plan, also von dort, wo auch
die Bilddatei ihren Namen bekommt.

## Warum keine Prüfung das sah

Derselbe Satz wie in 1.69.0, mit einem anderen Nachbau:

```js
window.__geschrieben.push({ pfad, groesse, typ });   // kein Inhalt
```

Was nicht festgehalten wird, lässt sich nicht prüfen. Der Nachbau hält
jetzt auch den Inhalt fest – und die ersten **Bytes**, denn `Blob.text()`
entfernt ein führendes BOM. Das ist die UTF-8-Dekodierung der
Spezifikation und kein Fehler; wer wissen will, ob das BOM in der Datei
steht, muss die Bytes ansehen. (Die erste Fassung dieser Prüfung fiel
genau darauf herein.)

Geprüft wird jetzt beides: die `index.csv` **mit** BOM (seit 1.72.0), die
`index.json` **ohne** – JSON darf keines haben.

## Die BPMN-Datei

Hier war nichts zu beanstanden. Geprüft wurde, was darüber entscheidet, ob
ein Werkzeug die Datei öffnet oder eine leere Fläche zeigt:

| | |
| --- | --- |
| Flüsse ins Leere | keine – jeder `sourceRef`/`targetRef` trifft einen Knoten |
| Formen ohne Element | keine – jedes `bpmnElement` gibt es |
| Knoten ohne Form | keine – jeder steht auch auf der Fläche |
| `BPMNDiagram` | vollständig, mit Koordinaten und Wegpunkten |
| Platzhalter | schlichtes `task` statt `userTask`, Text steht drin |

Die bisherige Prüfung **zählte** acht Flüsse und acht Formen. Das bleibt
richtig, auch wenn ein Fluss ins Leere zeigt. Jetzt wird der Zusammenhang
geprüft, nicht die Zahl.

Dabei hatte ich zuerst einen Fehler zu finden geglaubt: ein Schritt der
Art `verzweigung` kam in der Datei nicht an. Es gibt diese Art nicht –
Strecken kennen `schritt` und `platzhalter`. Meine Eingabe war erfunden,
und die Seite hat sie zu Recht übergangen.

## Grenzen

* Die BPMN-Datei ist **strukturell** geprüft, nicht in einem BPMN-Werkzeug
  geöffnet. Hier steht keines.
* Der Ordner wurde mit einem Bestand **ohne Labels** geschrieben. Das
  Vorgabemuster legt ihn dann vier Ebenen tief unter
  `ohne-sparte/ohne-sprache/<kapitel>/ohne-rolle/`. Das ist richtig
  gerechnet und sieht trotzdem seltsam aus; geändert wurde nichts, weil
  das Muster frei wählbar ist und ein anderer Vorgabewert jeden
  überraschen würde, der sich auf den heutigen verlässt.
* Gemessen mit elf Bildern. Ein Ordner mit dreihundert wurde nicht
  geschrieben.
